\chapter{Analisi dei requisiti}
\label{chap:analisi-requisiti}

\textit{Questo capitolo presenta gli use case rilevanti per le attività di ottimizzazione ed evoluzione 
svolte sul firmware embedded del dispositivo EggLog Motion Core (d'ora in poi solo EggLog) durante il 
periodo di tirocinio, insieme alla relativa analisi dei requisiti.}

\section{Analisi degli utenti}
Prima di affrontare le fasi di progettazione e sviluppo, è opportuno individuare a chi si rivolge il 
prodotto finale, soprattutto quando questo non è ancora disponibile sul mercato.

L'azienda ha già condotto uno studio preliminare del pubblico di riferimento, individuando tre principali 
categorie di utenti:
\begin{itemize}
    \item i \textbf{centri di \textit{coaching}}, che possono impiegare i dati sensoriali raccolti come supporto didattico 
    per il miglioramento tecnico dei piloti.
    \item i \textbf{team organizzatori di eventi motociclistici}, interessati a raccogliere dati telemetrici 
    dettagliati sui partecipanti alle gare;
    \item i \textbf{piloti semi-professionisti}, che possono sfruttare EggLog per valutare le proprie prestazioni 
    durante sessioni di allenamento o competizioni ufficiali;
\end{itemize}

\section{Lista degli \textit{use case}}

Nel contesto dell'ingegneria del software, uno \textit{use case} rappresenta una descrizione strutturata delle 
interazioni tra un attore e un sistema, finalizzate al raggiungimento di uno specifico obiettivo. 
L'attore può essere un utente, un altro sistema o qualsiasi entità esterna che interagisce con il software. 
La definizione degli \textit{use case} consente di individuare e descrivere in modo chiaro i requisiti funzionali
 del sistema.

Ogni \textit{use case} è caratterizzato dai seguenti elementi:
\begin{itemize}
    \item una \textbf{descrizione} dell'interazione tra l'attore e il sistema;
    \item lo \textbf{scopo} per cui l'attore fa tale interazione;
    \item i \textbf{criteri di accettazione}, ossia le condizioni che devono essere soddisfatte affinché 
    il caso d'uso possa considerarsi completato con successo.
\end{itemize}

Di seguito sono riportati esclusivamente gli use case relativi alle attività di ottimizzazione ed evoluzione 
effettivamente svolte durante il tirocinio.

\paragraph{UC1 -- Acquisizione binaria dei dati sensore}
\label{uc:uc_acquisizione_binaria}
\textbf{Descrizione:} EggLog deve acquisire i campioni dei sensori e serializzarli in un buffer 
in formato binario anziché testuale.

\textbf{Scopo:} Ridurre la dimensione del buffer necessario in RAM, il carico computazionale sulla CPU per 
la serializzazione dei dati e, di conseguenza, il consumo energetico del dispositivo.

\textbf{Criteri di accettazione:}
\begin{itemize}
    \item I dati acquisiti devono essere serializzati in formato binario nativo, non testuale;
    \item Il buffer in RAM utilizzato per l'acquisizione deve avere una dimensione ridotta rispetto 
    all'equivalente in formato testuale;
    \item La procedura di acquisizione non deve introdurre perdita di campioni rispetto alla configurazione 
    precedente;
    \item Ogni campione deve mantenere l'associazione con il proprio timestamp.
\end{itemize}

\paragraph{UC2 -- Registrazione dei dati su SD in formato binario}
\label{uc:uc_storage_binario_sd}
\textbf{Descrizione:} EggLog deve scrivere sulla scheda microSD i dati acquisiti in formato 
binario anziché testuale.

\textbf{Scopo:} Ridurre il numero e la durata delle operazioni di scrittura su SD e lo spazio di 
archiviazione occupato.

\textbf{Criteri di accettazione:}
\begin{itemize}
    \item I dati devono essere persistiti su SD in formato binario;
    \item La struttura dei file binari deve permettere una successiva decodifica coerente dei dati;
    \item La procedura di scrittura non deve causare perdita di dati rispetto al formato precedentemente 
    utilizzato.
\end{itemize}

\paragraph{UC3 -- Acquisizione dati dal bus CAN (ECU)}
\label{uc:uc_lettura_can_ecu}
\textbf{Descrizione:} EggLog deve poter leggere i dati esposti dalla centralina motore (ECU) 
tramite bus CAN.

\textbf{Scopo:} Arricchire il set di dati raccolti con i parametri del veicolo (es. regime motore, velocità), 
sincronizzati con gli altri sensori.

\textbf{Criteri di accettazione:}
\begin{itemize}
    \item I dati devono essere reperibili continuamente durante la sessione;
    \item Ogni rilevazione deve essere associata a un timestamp coerente con gli altri sensori;
    \item I messaggi CAN non riconosciuti o malformati devono essere scartati senza interrompere 
    l'acquisizione;
    \item I dati acquisiti devono essere memorizzati con lo stesso formato binario adottato per gli altri 
    sensori.
\end{itemize}

\paragraph{UC4 -- Gestione dello stato del firmware tramite LED}
\label{uc:uc_stato_led}
\textbf{Descrizione:} EggLog deve pilotare il LED integrato sulla scheda ESP32-S3 per 
comunicare lo stato corrente del dispositivo.

\textbf{Scopo:} Fornire un feedback visivo immediato all'utente sullo stato operativo del dispositivo, 
senza necessità di strumenti esterni.

\textbf{Criteri di accettazione:}
\begin{itemize}
    \item Ogni stato rilevante del dispositivo (es. inizializzazione, registrazione attiva, errore, batteria 
    scarica) deve corrispondere a un pattern del LED distinguibile dagli altri;
    \item Il cambio di stato deve riflettersi sul LED entro un tempo trascurabile per l'utente;
    \item In presenza di più condizioni contemporanee, deve essere mostrato lo stato a priorità più alta.
\end{itemize}

\paragraph{UC5 -- Configurazione dell'output rate (ODR) dei sensori}
\label{uc:uc_config_odr}
\textbf{Descrizione:} L'utente deve poter modificare la frequenza di campionamento (ODR) dei sensori del 
dispositivo.

\textbf{Scopo:} Adattare la frequenza di acquisizione alle esigenze specifiche della sessione, bilanciando 
dettaglio dei dati e consumo di risorse.

\textbf{Criteri di accettazione:}
\begin{itemize}
    \item L'operazione deve essere eseguibile dall'utente in qualunque momento;
    \item La frequenza impostabile deve rientrare nell'intervallo 10-100 Hz;
    \item La nuova configurazione deve essere salvata in memoria persistente e applicata alle acquisizioni 
    successive;
    \item Un valore richiesto fuori dall'intervallo supportato deve essere rifiutato, mantenendo la 
    configurazione precedente.
\end{itemize}

\paragraph{UC6 -- Sospensione dell'acquisizione sensori in stato di inattività}
\label{uc:uc_sospensione_sensori}
\textbf{Descrizione:} EggLog deve sospendere automaticamente l'acquisizione dei sensori quando 
rileva che il veicolo è fermo.

\textbf{Scopo:} Ridurre il consumo energetico del dispositivo durante i periodi di inattività del veicolo 
(es. sosta in un parcheggio).

\textbf{Criteri di accettazione:}
\begin{itemize}
    \item Il dispositivo deve rilevare l'assenza di variazioni significative nei dati dell'accelerometro per 
    un intervallo di tempo configurabile (default: 10 minuti);
    \item Al superamento di tale intervallo, l'acquisizione dei sensori non essenziali deve essere sospesa 
    automaticamente;
    \item Il dispositivo deve riattivare automaticamente l'acquisizione al rilevamento di un nuovo movimento;
    \item La sospensione automatica deve poter essere disabilitata su richiesta dell'utente.
\end{itemize}

\paragraph{UC7 -- Calibrazione dei sensori}
\label{uc:uc_calibrazione_sensori}
\textbf{Descrizione:} EggLog deve eseguire una procedura di calibrazione dei sensori a inizio 
sessione o alla prima configurazione del dispositivo.

\textbf{Scopo:} Garantire l'accuratezza delle misurazioni compensando gli offset e le derive dei sensori.

\textbf{Criteri di accettazione:}
\begin{itemize}
    \item La calibrazione deve essere eseguita automaticamente alla prima configurazione del dispositivo o 
    all'avvio di una sessione priva di calibrazione valida;
    \item I parametri di calibrazione ottenuti devono essere memorizzati in memoria persistente;
    \item I parametri di calibrazione memorizzati devono essere applicati alle letture sensore nelle sessioni 
    successive;
    \item Se la calibrazione fallisce (es. dispositivo in movimento durante la procedura), la procedura deve 
    essere ripetuta prima di iniziare l'acquisizione.
\end{itemize}

\section{Tracciamento dei requisiti}
Un requisito di un sistema software è definito da una descrizione di cosa il sistema dovrebbe fare, i 
servizi che esso fornisce e i vincoli a cui deve sottostare. Più in particolare, un requisito si può 
riconoscere come:
\begin{itemize}
    \item una capacità necessaria a un utente per risolvere un problema o raggiungere un obiettivo,
    \item una capacità del sistema stesso di adempiere a un obbligo prestabilito.
\end{itemize}

In questa sezione si riporta la lista di requisiti rilevata in seguito all'analisi dell'utenza e degli use 
case; i requisiti sono identificati da un codice definito con la seguente nomenclatura:
\begin{center}
R(Tipo)(Urgenza)-(Codice)
\end{center}
Dove:
\begin{itemize}
    \item (Tipo) è una lettera rappresentante la tipologia di requisito:
    \begin{itemize}
        \item F per i requisiti funzionali,
        \item N per i requisiti non funzionali,
        \item V per i requisiti di vincolo,
    \end{itemize}
    \item (Urgenza) è una lettera rappresentante l'urgenza del requisito:
    \begin{itemize}
        \item O per i requisiti obbligatori,
        \item D per i requisiti desiderabili,
        \item F per i requisiti facoltativi,
    \end{itemize}
    \item (Codice) è un numero identificativo sequenziale.
\end{itemize}
